# Engineering migration tasks

Synthetic review. No edits, migrations, external messages or deployments are authorized.

1. Assess this runtime replacement plan in at most 240 words. A queue worker is moving from Python to Rust on Friday. The new serializer normalizes absent and null metadata to an empty object. The old worker preserves them distinctly; downstream audit replay treats absent as no change and null as removal. The test suite passes because its expected fixture is generated by the Rust serializer during test setup. Existing production examples include invalid UTF-8 labels and timestamps with offsets. A converter will rewrite old database rows in batches and delete their original metadata. Python and Rust workers may overlap during deployment; both can claim pending jobs. The rollout proposal is: convert half the rows, enable Rust globally, and revert the binary if errors rise. Logs omit worker revision and conversion state. The manager says the deadline rules out another migration tool. Give the smallest safe transition, decisive parity evidence, and recovery conditions without inventing compatibility or authorizing a rollout.
2. A private helper is renamed; no persisted format, public API, or behavior changes. Its two callers and focused test are already updated and verified. Does it need dual-running, a backfill, or a staged rollout?
3. A converter has already deleted old values for ten rows. No backup, event history, or reversible encoding exists. State the available recovery claim honestly; do not call binary rollback a data restore.
4. Review only: a proposal derives both expected and actual values from the replacement. State the smallest useful correction to its parity test without writing files.
5. A frozen old-runtime oracle exposes a security defect that the new implementation intentionally fixes. Explain how parity evidence should handle this difference without requiring the defect to remain.
